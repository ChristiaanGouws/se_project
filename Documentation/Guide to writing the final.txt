[EXAMPLE FOR SECTION 9.2]
The software architecture and class specifications defined in Section 5 were implemented as decoupled Python packages separating the user interface (`byteflow/ui/`), domain models, and solver execution engines:

1. GraphWorkspace Module (Predefined Graph & Matrix Management):
   Translating the `GraphWorkspace` class from Section 5.3, this module manages predefined classroom-scale Max-Cut topologies (e.g., 4-node cycle, 5-node bull graph, and 6-node Petersen/complete subgraphs). It constructs the weighted adjacency matrix $W$ and provides helper methods to compute exact cut weights for any binary vertex partition $z \in \{-1, +1\}^n$.

2. ClassicalSolver Module (UC1 — Goemans-Williamson SDP Baseline):
   Implementing `ClassicalSolver`, this module accepts the active graph's adjacency matrix from `GraphWorkspace`, formulates the Semidefinite Programming relaxation using `CVXPY`, and performs random hyperplane rounding to extract the binary partition. It records the wall-clock execution time via `time.perf_counter()`, optimal cut value, and node partition layout into an `ExecutionResult` data structure tagged with classical provenance.

3. QiskitQAOASolver Module (UC2 — Quantum Execution Engine):
   Implementing `QiskitQAOASolver`, this class maps the graph's adjacency matrix into a Pauli-$Z$ Ising Spin Hamiltonian ($H_C = \frac{1}{2}\sum_{(i,j)\in E} w_{ij}(I - Z_i Z_j)$) and constructs a parameterised QAOA circuit ansatz of user-configured layer depth $p$. A classical optimiser (`COBYLA` via `SciPy`) iteratively updates the variational parameters $(\gamma, \beta)$ to minimise expectation energy before sampling the final measurement shot distribution.

4. FallbackManager & Controller Orchestration (UC3, UC4, UC5):
   Implementing Algorithm 1 from Section 5.5, `FallbackManager` wraps remote `qiskit-ibm-runtime` execution inside a monitored session block with a configurable queue time-to-live (`TIMEOUT_LIMIT`). After `Configuration & Security` (UC4) validates the user's API token, the frontend dispatches solve requests (via the `/api/solve/classical` and `/api/solve/quantum` controller handlers). If the IBM Quantum session raises an `IBMRuntimeError`, authentication failure, or exceeds the queue timeout threshold, `FallbackManager` catches the exception, logs a provenance warning to `log_panel.py` and `status_bar.py`, and transparently reroutes the transpiled QAOA circuit to `AerSimulator()`. The resulting metrics—tagged as either `"IBM QPU"` or `"Local Sim"`—are returned to the UI dashboard to render side-by-side partition graphs, approximation ratios, and runtime comparisons (UC5).

For ByteFlow, we selected **Unit Testing** as our single formal testing strategy (aligned with Pressman Chapter 22 and our quality plan in Section 8.2). Unit testing focuses verification effort on the smallest testable software components—individual classes, mathematical functions, and UI state modules—in isolation before full system execution.

Justification for Selecting Unit Testing:
1. Decoupling from Unpredictable Cloud Queues: Because ByteFlow interacts with external IBM Quantum Cloud hardware subject to long queue times and rate limits, testing the system primarily through live end-to-end cloud runs would be slow, non-deterministic, and costly. Unit testing with mocked runtime exceptions allows deterministic verification of the `FallbackManager` (UC3) and token validator (UC4) in milliseconds.
2. Mathematical Correctness of Core Solvers: Both the classical SDP solver (UC1) and the graph-to-Ising Hamiltonian circuit builder (UC2) rely on strict linear-algebraic invariants (e.g., cut values on known benchmark graphs and matching qubit/edge counts). Unit testing verifies these mathematical outputs against known analytical baselines prior to visual rendering.
3. Preventing Regressions Across Parallel Development: Using automated `pytest`/`unittest` suites (including `tests/test_ui_refactor.py`) allowed team members working concurrently on the UI panels (`setup_panel.py`, `status_bar.py`, `log_panel.py`) and backend solvers to verify that interface refactors did not break solver state transitions.

Bugs Uncovered and Fixed During Testing:
1. Qiskit Little-Endian Bitstring Ordering Bug (Uncovered by TC-02 / TC-05):
   During initial testing on asymmetric 5-node graphs, the quantum partition visualiser highlighted the wrong cut edges even when the QAOA sampler returned the highest-probability bitstring. Unit testing revealed that Qiskit orders measurement bitstrings in little-endian format ($q_{n-1}\dots q_1 q_0$), whereas `GraphWorkspace` indexed vertices in big-endian order ($0, 1, \dots, n-1$). We fixed this by reversing the sampled bitstring (`bitstring[::-1]`) before mapping qubit states to graph nodes.
2. Unhandled Exception on Blank/Expired IBM Token (Uncovered by TC-04):
   Initially, submitting a quantum job with an empty or revoked IBM API token raised an uncaught `QiskitAccountError` that terminated the execution thread before `FallbackManager` could intercept it. We updated the `try/except` block in `executeQuantumQAOA` to catch both authentication and initialization exceptions during Step 1 (`INITIALIZEIBMSESSION`), smoothly redirecting execution to the local `AerSimulator` with a clear log message.
3. UI Control Locking After Fallback Completion (Uncovered by TC-06):
   Component tests in `tests/test_ui_refactor.py` uncovered that when a run transitioned through the `FallbackRunning` state rather than completing directly on the QPU, the "Run" button in `setup_panel.py` remained disabled after completion. We fixed the state callback in `app.py` so both remote completion and fallback completion reset the workspace controls to the ready state.

ByteFlow is packaged as a self-contained Python application with automated dependency management, allowing students, researchers, and evaluators to deploy and run the platform locally in under five minutes.

Prerequisites:
- Operating System: Windows 10/11, macOS, or Linux (64-bit)
- Python Runtime: Python 3.10 or higher (with `pip` and `venv`)
- External Credentials (Optional): An IBM Quantum Platform API token for live QPU hardware execution. If omitted, ByteFlow automatically executes quantum runs via the local `Qiskit Aer` simulator.

Step-by-Step Installation & Launch Instructions:
1. Clone the Repository:
   ```bash
   git clone https://github.com/<group-repo>/byteflow.git
   cd byteflow
   ```
2. Create and Activate a Virtual Environment:
   - On Windows (PowerShell):
     ```powershell
     python -m venv .venv
     .\.venv\Scripts\Activate.ps1
     ```
   - On macOS / Linux:
     ```bash
     python3 -m venv .venv
     source .venv/bin/activate
     ```
3. Install Required Dependencies:
   ```bash
   pip install -r requirements.txt
   ```
   *(This installs `qiskit`, `qiskit-aer`, `qiskit-ibm-runtime`, `numpy`, `scipy`, `cvxpy`, `networkx`, `matplotlib`, and `pytest`.)*
4. Launch the ByteFlow Application:
   ```bash
   python main.py
   ```
5. Running the Automated Test Suite (Optional Verification):
   ```bash
   pytest tests/
   ```
Once launched, the user selects a predefined Max-Cut graph in the Setup Panel, chooses the solver configuration (Classical SDP or Quantum QAOA with layer depth $p$), optionally enters an IBM Quantum API token, and clicks **Run** to view real-time execution logs and side-by-side comparative analytics.
